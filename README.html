DeliveryFlow Local Data Platform

Multi-Application Stream Architecture Update

DeliveryFlow is now being built as a platform that can support multiple applications rather than only a single delivery-stream demo. The default operator flow remains unchanged:


Copy-Item .env.example .env
make config
make up
make health
make submit-flink-job
make produce
make spark-daily-kpi
make import-superset-assets
make console

Fleet vehicle telemetry is a second stream application and runs independently without changing the delivery job:


make submit-flink-job APP=fleet
make produce APP=fleet
make test-e2e APP=fleet

This separation is important at a scale of 300-500 tables: application metadata is stored under configs/applications/, dataset metadata under configs/datasets/, and JSON contracts under src/contracts/<domain>/. The delivery-events topic carries delivery lifecycle events, while vehicle-telemetry-events carries fleet telemetry. ClickHouse follows the same ownership boundary: delivery.* serves delivery operations and fleet.* serves fleet telemetry.

Fleet telemetry assets:

  • configs/applications/fleet.yaml
  • configs/datasets/fleet/vehicle_telemetry.yaml
  • src/contracts/fleet/vehicle_telemetry_v1.schema.json
  • services/flink/src/main/java/local/deliveryflow/VehicleTelemetrySqlJob.java
  • fleet.vehicle_telemetry_events
  • fleet.vehicle_current_state
  • fleet.vehicle_health_alerts
  • fleet.vehicle_metrics_5m

DeliveryFlow is a data engineering project built on local Docker Compose. It demonstrates both real-time delivery monitoring and daily batch analytics for the logistics domain.

This README is intended for first-time users. It explains where to start, what each service does, the order in which make commands are run, and how to verify the pipelines.

Brief Summary

Architecture Concepts

When exploring DeliveryFlow, these core technologies work together across the streaming and batch layers:

  • Kafka: Receives events from the producer and acts as the distributed event transport layer.
  • Flink: Consumes events from Kafka and processes them in real time using event-time semantics.
  • ClickHouse: Serves as the operational and BI serving database for fast analytical queries.
  • Apache Iceberg: The open table format used for analytical datasets in the Data Lake.
  • MinIO: Stores the physical Parquet data files and Iceberg metadata in local S3-compatible object storage.
  • Nessie: Acts as the transactional Iceberg catalog and tracks table metadata references and git-like branches.
  • Spark: Reads and writes Iceberg tables and calculates daily batch KPIs.
  • Airflow: Orchestrates scheduled batch workflows and triggers Spark jobs.
  • PostgreSQL: Stores metadata for Airflow and Nessie, and hosts relational source tables for batch seeding.
  • Superset: Connects to ClickHouse to provide operational BI dashboards and reports.

Practical Data Flow Examples

Application 1: Delivery Operations (Default Stream Pipeline)


delivery-events -> Flink DataStream -> delivery.*

Example flow:

  • A delivery event is created by the producer: VEHICLE_DEPARTED.
  • The event is published to the delivery-events Kafka topic.
  • Kafka stores the event and Flink consumes it.
  • Flink processes the event, validates the schema contract, and updates delivery.delivery_current_state in ClickHouse.
  • Superset queries ClickHouse to display the latest active delivery status on the dashboard.

Application 2: Fleet Telemetry (Multi-Application Stream Pipeline)


vehicle-telemetry-events -> Flink SQL -> fleet.*

Example flow:

  • A telemetry event is created by the Fleet producer: {"vehicle_id": "TRK-101", "speed_kmh": 88.5, "engine_temp_c": 98.2}.
  • The event is published to the vehicle-telemetry-events Kafka topic.
  • Flink SQL consumes the event, assigns event-time watermarks, computes 5-minute aggregations, and evaluates health alert conditions.
  • Flink writes the current state to fleet.vehicle_current_state and alerts to fleet.vehicle_health_alerts in ClickHouse.

Executive Overview

        

          DeliveryFlow demonstrates modern data engineering patterns applied to modern supply chain operations. It solves the dual-speed analytical dilemma:
        

        
    
          
  • Immediate Operational Dispatch: Sub-second state tracking of delivery vehicles, status transitions, traffic conditions, and sensor anomalies via Apache Kafka, Apache Flink, and ClickHouse.
    • 
          
  • Strategic Long-Term Analytics: Cost-effective historical aggregations, dimensional modeling, and auditable metrics via Apache Iceberg, MinIO object storage, Project Nessie, PySpark, and Apache Airflow.
    • 
          
  • Declarative BI-as-Code: Operational dashboards provisioned automatically into Apache Superset via YAML definitions and REST APIs without manual UI clicking.

Prerequisites

Local operation requires:

  • Docker Desktop
  • Docker Compose v2
  • make
  • Git
  • Sufficient RAM and disk space

If a port conflict occurs, change the ports in .env. The ports most likely to conflict are:

  • AIRFLOW_WEB_PORT=8080
  • FLINK_UI_PORT=8081
  • SPARK_MASTER_UI_PORT=8082
  • KAFKA_UI_PORT=8083
  • SUPERSET_PORT=8088
  • POSTGRES_AIRFLOW_PORT=15432
  • POSTGRES_SOURCE_PORT=15433

Step 1: Prepare the Environment File

Before the first startup:


Copy-Item .env.example .env

The .env file stores all local Docker Compose configuration:

  • image names
  • ports
  • database names
  • local user/password values
  • Kafka topic name
  • producer parameters
  • Superset parameters

Do not commit .env to Git.

Step 2: Validate the Compose Configuration

Before starting the platform:


make config

This command runs:


docker compose config

This checks that:

  • .env values are read correctly.
  • docker-compose.yml has valid syntax.
  • volume, port, service, and environment mappings are valid.

If this reports an error, fix it before running make up.

Import Superset objects as BI-as-code:


make import-superset-assets

This command creates or updates database, dataset, chart, and dashboard objects through the Superset REST API using configs/superset/deliveryflow_bi.yaml.

This import means the dashboard does not need to be created manually in the Superset UI. The importer manages:

  • DeliveryFlow ClickHouse database connection.
  • Five datasets based on five ClickHouse views.
  • Five statistical charts.
  • The DeliveryFlow Operations Dashboard dashboard.
  • Adhoc metric formatting for chart metrics. For example, the event_count column is written as SUM(event_count) and delay_rate as AVG(delay_rate) in the chart.
  • Datetime metadata for timeseries charts. In the Hourly Delivery Event Volume chart, event_hour is both the dataset temporal column and the chart x_axis / granularity_sqla value.

Prepared views for the dashboard:

  • delivery.v_delivery_status_overview
  • delivery.v_delay_by_region
  • delivery.v_vehicle_utilization
  • delivery.v_warehouse_daily_kpi
  • delivery.v_delivery_event_volume

To verify the views:

Architecture Components & Technology Stack


        

          

            
Ingestion

            
Apache Kafka (KRaft)

            

              Single-broker KRaft cluster running without ZooKeeper dependency. Provides partition keying, durable replication, and decoupled message buffering.
            

          


          

            
Stream Processing

            
Apache Flink

            

              Stateful stream compute engine utilizing Java DataStream for delivery state machines and Flink SQL for telemetry tumbling window aggregations.
            

          


          

            
Serving Layer

            
ClickHouse Analytics

            

              Columnar analytics database executing sub-second aggregations. Uses MergeTree for historical logs and ReplacingMergeTree for state deduping.
            

          


          

            
Lakehouse Storage

            
Iceberg + Nessie + MinIO

            

              ACID lakehouse format storing Parquet files in MinIO S3 object storage with Git-like catalog branching, time travel, and snapshot isolation via Project Nessie.
            

          


          

            
Batch Engine

            
Apache Spark (PySpark)

            

              Executes daily logistics KPI aggregations joining ClickHouse events and PostgreSQL dimensional tables, writing committed Iceberg snapshots.
            

          


          

            
Batch Orchestration

            
Apache Airflow

            

              Batch workflow scheduler with LocalExecutor. Monitors ClickHouse source readiness sensors and triggers distributed Spark batch jobs.
            

          


          

            
Relational Sources

            
Dual PostgreSQL Services

            

              Strict container isolation: postgres-source (port 5433) hosts transactional dimensional tables, while postgres-airflow (port 5434) manages Airflow state.
            

          


          

            
Visualization

            
Apache Superset

            

              BI-as-Code dashboard platform querying prepared ClickHouse views to render 5 executive operational charts and dispatch summaries.

The import creates the DeliveryFlow ClickHouse database connection, five datasets, five charts, and the DeliveryFlow Operations Dashboard in Superset.


The importer also normalizes Superset chart parameters:


    

  • Human-readable metric names stored in YAML are converted to Superset adhoc metric format.
    • 

  • SUM(...) is used for count and sum columns.
    • 

  • AVG(...) is used for columns with an avg_ prefix or _rate suffix.
    • 

  • Time columns such as event_hour and business_date are recorded as temporal columns in dataset metadata.
    • 

  • Hourly Delivery Event Volume uses x_axis: event_hour, granularity_sqla: event_hour, and time_grain_sqla: PT1H.
    • 



This behavior prevents the following Superset errors:



Metric 'event_count' does not exist
Metric 'delay_rate' does not exist
Datetime column not provided as part table configuration and is required by this type of chart

Troubleshooting Guide


Issue 1: Events Do Not Reach ClickHouse


Problem: Events are produced, but delivery.delivery_events in ClickHouse remains empty.


Possible Cause: The Flink streaming job is not running, or Kafka consumer connectivity failed.


How to Check: Check Kafka and Flink job manager logs:



make logs-kafka
make logs-flink



Inspect ClickHouse row count:



docker compose exec clickhouse clickhouse-client --query "SELECT count() FROM delivery.delivery_events"



How to Fix: Submit the Flink streaming job and send test stream events:



make submit-flink-job
make produce-stream



Expected Result: ClickHouse returns a positive row count in delivery.delivery_events.


Issue 2: Fleet Telemetry Does Not Appear in ClickHouse


Problem: Telemetry events for APP=fleet do not appear in fleet.vehicle_telemetry_events.


Possible Cause: The VehicleTelemetrySqlJob Flink SQL application was not submitted.


How to Check: Check Flink running jobs in the Flink Web UI (http://localhost:8081) or logs:



make logs-flink



How to Fix: Submit the Fleet Flink SQL job and trigger fleet data generation:



make submit-flink-job APP=fleet
make produce APP=fleet



Expected Result: Rows appear in fleet.vehicle_telemetry_events and fleet.vehicle_current_state.


Issue 3: Superset Views or Metrics Return Errors


Problem: Superset dashboard charts display metric errors, missing datasets, or column type mismatches.


Possible Cause: Superset metadata assets are out of sync with ClickHouse serving tables.


How to Check: List existing serving tables in ClickHouse:



docker compose exec clickhouse clickhouse-client --query "SHOW TABLES FROM delivery"



How to Fix: Re-import the BI-as-code configuration assets:



make import-superset-assets



Then hard-refresh your browser tab (Ctrl + F5).


Expected Result: All 5 delivery charts render without errors on the Superset dashboard (http://localhost:8088).


Issue 4: Schema Mismatch from Stale Docker Volumes


Problem: ClickHouse or PostgreSQL container startup fails or retains outdated table definitions.


Possible Cause: Named Docker volumes from previous runs contain old schema state.


How to Check: Inspect volume definitions and container errors:



docker compose ps
make logs-all



How to Fix: Purge stale containers and volumes, then recreate the platform:



make purge
make up
make health



Expected Result: Clean initialization scripts execute on first boot, and all tables match current schema contracts.

Operational Safety: make clean vs. make purge

⚠ CRITICAL SAFETY WARNING

Always distinguish between routine maintenance and destructive factory resets:

  • make clean (Safe): Stops containers and removes network bridges. Preserves all named Docker volumes. All PostgreSQL databases, ClickHouse tables, MinIO objects, and Nessie commits remain completely intact.
  • make purge (Destructive): Stops containers, removes networks, and deletes all named Docker volumes (--volumes). Wipes all databases and resets the platform to an empty factory state. Use only when resolving schema corruption or performing fresh benchmark runs.

Scaling to 300–500 Datasets

DeliveryFlow is architected with a metadata-driven control plane designed to onboard hundreds of tables without duplicating infrastructure code:

  • Generic ETL Framework: Standard source-to-lakehouse ingestion runs via shared PySpark readers/writers driven by dataset YAML specifications.
  • Domain Event Grouping: Stream pipelines avoid the anti-pattern of 1 Kafka topic and 1 Flink job per table; instead, events are grouped by business capability with partition keying.
  • Lakehouse Hierarchical Namespaces: Tables are partitioned systematically (<app>.<layer>.<dataset>) with scheduled compaction and snapshot retention routines.

For complete scaling patterns and governance rules, visit the dedicated Multi-App Scalability Blueprint.
