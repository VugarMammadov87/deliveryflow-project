Architecture Decisions

ADR-000: Multi-Application Control Plane

DeliveryFlow is no longer documented as a single-application demo. The repository now has a small control-plane structure that separates application metadata, dataset metadata, and event contracts:


configs/applications/
configs/datasets/
src/contracts/<domain>/

Decision:

  • Keep the local platform simple, but make application ownership explicit.
  • Keep delivery as the default application.
  • Add fleet telemetry as an independent second application.
  • Select non-default app runtime with APP=fleet.
  • Keep Kafka topics domain-oriented, not one topic per table by default.
  • Keep ClickHouse serving schemas domain-oriented: delivery.* and fleet.*.

The first implementation of this decision is VehicleTelemetrySqlJob, a Java Flink SQL/Table API job that reads vehicle-telemetry-events and writes to the fleet database. This is intentionally separate from DeliveryStreamingJob, which remains the Java DataStream implementation for delivery events.

This decision prepares the project for 300-500 table growth without requiring one Python script, one Spark job, one Flink job, one Airflow DAG, and one Superset file per table.

This document explains the main architecture decisions made for DeliveryFlow. The goal is to build a platform that is simple, functional, and aligned with data engineering principles for the local lab.

ADR-001: Kafka KRaft Broker

Kafka runs as a single KRaft broker. ZooKeeper is not included in the local lab.

Rationale:

  • Fewer services.
  • Simpler local bootstrap.
  • A setup closer to the modern Kafka deployment model.

Topic strategy:


delivery-events

This topic carries delivery lifecycle events. The event key is delivery_id.

ADR-002: Flink Stream Processing

Flink was selected for real-time event processing.

Rationale:

  • Natural integration with Kafka as a source.
  • Event-time and watermark support.
  • Keyed stream processing.
  • Checkpointing support.
  • A suitable model for a real-time ClickHouse sink.

In this project, Flink:

  • Consumes Kafka events.
  • Parses JSON.
  • Validates schema_version = 1.
  • Builds delivery and vehicle state.
  • Writes to ClickHouse.

ClickHouse views:

  • v_delivery_status_overview

ADR-004: Spark Batch Processing

Spark was selected for daily KPI and lakehouse writes.

Rationale:

  • A broad ecosystem for batch aggregation.
  • Iceberg integration.
  • The ability to read from ClickHouse over JDBC.
  • The ability to be controlled from Airflow with spark-submit.

Spark job:


src/etl/apps/daily_kpi_job.py

Spark output:

  • nessie.bronze.raw_delivery_events
  • nessie.gold.daily_delivery_kpi
  • delivery.daily_delivery_kpi

ADR-005: Iceberg + Nessie + MinIO Lakehouse

The lakehouse layer has three parts:

  • Iceberg table format.
  • Nessie catalog.
  • MinIO S3-compatible object storage.

  • Iceberg provides the analytical table format.
  • Nessie manages the catalog and versioned metadata.

ADR-006: PostgreSQL Database Separation

There are two PostgreSQL services:

  • postgres-airflow
  • postgres-source

postgres-airflow is used only for Airflow metadata.

postgres-source stores two databases:

  • logistics_source
  • nessie_metadata

This separation makes lifecycle and ownership clearer.

ADR-007: Airflow Batch Orchestration

Airflow provides batch orchestration. It is not part of the streaming path.

Airflow responsibilities:

  • Schedule DAGs.
  • Check source readiness.
  • Submit Spark jobs.
  • Manage task status and retries.

In this project, Airflow uses LocalExecutor.

ADR-008: Superset BI Layer

Superset is the BI and dashboard layer.

Superset connects to ClickHouse and builds charts from prepared views.

Rationale:

  • Runs locally within Compose.
  • Works with ClickHouse.
  • Dashboards open in a browser.
  • Keeps the platform fully local.

Superset should not use raw Kafka, raw MinIO, or Iceberg metadata. Its approved data source is the ClickHouse serving layer.

BI objects are not stored as manual UI configuration. configs/superset/deliveryflow_bi.yaml is the repository source of truth for Superset database, dataset, chart, and dashboard definitions.

The make import-superset-assets workflow applies these decisions:

  • The superset-importer image is rebuilt first so YAML and Python importer changes are not left behind in an old image.
  • YAML metric names are written as chart-level adhoc metrics rather than Superset saved metrics. This prevents Metric 'event_count' does not exist and Metric 'delay_rate' does not exist errors.
  • SUM(...) is selected for count/sum columns, and AVG(...) for rate and average columns.
  • Temporal metadata remains explicit for timeseries charts. v_delivery_event_volume.event_hour is the dataset main_dttm_col and temporal column, and is also the chart's x_axis and granularity_sqla value.
  • business_date is recorded as a temporal column in the warehouse KPI dataset so future time-based charts follow the same rule.

The goal is for the Superset dashboard to import reproducibly into a clean environment: datasets, charts, and the dashboard should be created without metric or datetime metadata errors during chart rendering.

ADR-009: One Generator, Two Data Types

The generator remains a single application:


src/producers/synthetic_logistics_producer.py

It produces two data types:

  • Batch source rows.
  • Stream events.

Rationale:

  • The same synthetic business domain is preserved.
  • Batch and stream data remain logically consistent.
  • No additional application complexity is introduced in the local lab.

ADR-010: make clean and make purge Separation

make clean remains non-destructive:


docker compose down --remove-orphans

make purge is for a destructive reset:


docker compose down --volumes --remove-orphans --rmi local

Rationale:

  • Normal cleanup must not remove data volumes.
  • Schema changes need a separate, explicit target for a full reset.

The producer image contains only src/producers, kafka-python, and psycopg2-binary for PostgreSQL batch seeding. The ClickHouse client, Requests, PyYAML, health/E2E scripts, and Superset assets remain in the one-shot tooling image.

ADR-012: Modular Producer and Stable Continuous Rate

The producer entrypoint is preserved as the operator interface, while the implementation is split into configuration, event generation, PostgreSQL source, and Kafka streaming modules. These boundaries separate event contracts from transport and deployment configuration, enable focused unit tests, and provide a dedicated configuration adapter point for future metadata-driven configuration.

The continuous producer has a default interval of 60 seconds and publishes a batch of 10 events per interval. The batch-of-10 model directly expresses the T=00:00 -> 10 events, T=00:01 -> 10 events semantics and keeps rate tests simple. The publisher uses monotonic fixed deadlines instead of a chain of relative sleep(60) calls, so serialization and Kafka flush time do not create cumulative rate drift. The existing PRODUCER_CONTINUOUS_INTERVAL_SECONDS environment override is retained for backward compatibility, while PRODUCER_EVENTS_PER_INTERVAL controls the record count per interval.

Operational Rules

  • Run docker compose config --quiet after runtime configuration changes.
  • After schema changes, make purge may be required if an old volume remains.
  • ClickHouse views should be the basis for dashboards.
  • Batch jobs require source readiness; the KPI job may fail if ClickHouse delivery_events is empty.
  • Submit the Flink job before starting the producer for streaming.
ADR-003 Implemented

ClickHouse Columnar Serving Layer

Implemented

ClickHouse as Operational & Analytical Serving Layer

Context: Querying transactional databases (PostgreSQL) or object lakehouses (Iceberg on MinIO) for sub-second dashboard rendering results in excessive latency and lock contention.

Decision: ClickHouse serves as the unified real-time serving layer, utilizing MergeTree for append-only logs and ReplacingMergeTree for deduplicating state entities.

Consequences: Delivers sub-100ms analytical queries across millions of rows, powering Superset dashboards effortlessly.

Context: Neither transactional databases (Postgres) nor raw lake storage (S3/Iceberg) provide sub-second latency for live analytical dashboards under concurrent queries.

Decision: Deploy ClickHouse as the universal serving layer. Stream and batch pipelines write into ReplacingMergeTree tables and pre-aggregated views.

Consequences: Sub-second query times for Superset; complete decoupling of OLAP reporting from transactional and stream infrastructure.

ADR-004 Implemented

Apache Spark for Heavy Batch Transformations

Implemented

Apache Spark for Batch KPI Computation & Lakehouse ETL

Context: Daily logistics KPI computation requires complex joins between operational events and dimensional tables across multiple data stores.

Decision: PySpark 3.5.6 executes batch jobs submitted by Airflow, reading ClickHouse and PostgreSQL sources, and writing partitioned Iceberg snapshots.

Consequences: High-performance distributed batch compute with rich support for Iceberg table formats and SQL extensions.

Context: Large-scale historical KPI computation requires distributed execution, complex joins, and integration with open table formats.

Decision: Run an Apache Spark cluster (Master + Worker) executing standalone PySpark applications triggered by Airflow or Makefile commands.

Consequences: Enables reproducible batch processing across 3-tier Medallion tables; clean separation between stream compute (Flink) and batch compute (Spark).

ADR-005 Implemented

Apache Iceberg + Nessie + MinIO Lakehouse

Implemented

Open Lakehouse Architecture (Iceberg + Nessie + MinIO)

Context: Traditional Hive metastores are rigid, lack atomic transactions, and suffer from directory listing bottlenecks on cloud object stores.

Decision: Modern Lakehouse architecture combining Apache Iceberg table format, Project Nessie REST catalog (with PostgreSQL backend), and MinIO S3 object storage.

Consequences: ACID transactions, branch-based data versioning, schema evolution without rewriting data, and full compatibility with cloud data platforms.

Context: Raw object storage files lack ACID transaction guarantees, snapshot isolation, and versioning.

Decision: Pair Apache Iceberg table format with MinIO S3 object storage and Project Nessie catalog (providing Git-like branch/commit table semantics).

Consequences: Zero risk of partial writes or corrupted files; historical snapshot rollback; full open-source parity with cloud data lakehouses.

ADR-006 Implemented

Dual PostgreSQL Service Isolation

Implemented

PostgreSQL Container & Database Separation

Context: Combining operational business source tables and Airflow orchestrator metadata in a single database creates security risks and lifecycle coupling.

Decision: Separate into two distinct PostgreSQL containers: postgres-source (port 5433, hosting logistics_source and nessie_metadata) and postgres-airflow (port 5434, hosting Airflow state).

Consequences: Independent maintenance windows, clean failure isolation, and zero risk of schema poisoning between operational business data and workflow metadata.

Context: Mixing application source data with orchestration engine internals risks permission collisions and resource contention.

Decision: Isolate into two independent containers: postgres-source (hosting logistics_source and nessie_metadata) and postgres-airflow (hosting airflow_metadata).

Consequences: Prevents lock contention; allows independent data teardown without corrupting Airflow state.

ADR-007 Implemented

Apache Airflow for Batch Orchestration

Implemented

Apache Airflow as Pure Scheduler & Control Plane

Context: Scheduled batch jobs require SLA monitoring, automatic retries, task dependency graphs, and source readiness sensors.

Decision: Apache Airflow 2.10.5 orchestrates batch workflows using LocalExecutor, keeping Airflow strictly out of the streaming data path.

Consequences: Robust orchestration with clear separation: Airflow manages execution schedules, while Spark performs actual heavy data transformations.

Context: Running heavy data transformations inside Airflow workers degrades scheduler responsiveness and violates separation of concerns.

Decision: Restrict Airflow strictly to dependency scheduling, data readiness sensor checks, and external job submission (e.g., Spark submit).

Consequences: Airflow remains lightweight and stable; all heavy compute runs in Spark or ClickHouse.

ADR-008 Implemented

Apache Superset BI-as-Code

ADR-008 Implemented

Declarative BI-as-Code with Apache Superset

Context: Manual UI-based dashboard creation is error-prone, non-reproducible, and cannot be peer-reviewed in version control.

Decision: Treat dashboards as code via configs/superset/deliveryflow_bi.yaml and provision them via automated REST API scripts (make superset-import).

Consequences: 100% reproducible BI layer, automated test coverage, and clean version control for charts, metrics, and dashboards.

Context: Manual point-and-click dashboard creation cannot be version-controlled, automated in CI/CD, or replicated across developer environments.

Decision: Store all dashboards, charts, and dataset definitions in configs/superset/deliveryflow_bi.yaml and automate import via REST API script.

Consequences: 100% reproducible BI state via make import-superset-assets; zero drift between dev and staging dashboards.

ADR-009 Implemented

Single Synthetic Generator, Dual Data Modalities

ADR-009 Implemented

Unified Synthetic Data Generator

Context: Maintaining separate generators for relational source tables and Kafka event streams leads to entity ID divergence and broken joins.

Decision: A unified generator produces both transactional dimensional rows (PostgreSQL) and event streams (Kafka) using identical entity IDs (warehouses, vehicles, drivers).

Consequences: Guaranteed referential integrity between streaming events and batch dimension lookups.

Context: Generating stream events and relational batch records via disconnected scripts causes ID mismatches and impossible operational states.

Decision: Implement a single Python generator application supporting PRODUCER_MODE=streaming (Kafka) and PRODUCER_MODE=batch (PostgreSQL).

Consequences: Shared entities (delivery IDs, vehicle IDs) match perfectly across stream and batch paths, enabling end-to-end analytical joins.

ADR-010 Implemented

Explicit Separation of make clean and make purge

ADR-010 Implemented

Strict Separation of make clean and make purge

Context: Developers frequently wipe Docker volumes by mistake when attempting routine service restarts, causing loss of local experiment state.

Decision: make clean only stops containers and networks without touching volumes. make purge is explicitly reserved for destructive volume wipes and factory resets.

Consequences: Eliminates accidental data loss while retaining an easy one-command factory reset path.

Context: Accidental data loss occurs when teardown commands silently destroy persistent database volumes.

Decision: make clean stops containers and removes temporary files while preserving named Docker volumes. make purge is explicitly reserved for destructive full volume reset.

Consequences: Eliminates accidental data destruction during day-to-day restarts.

ADR-011 Implemented

Producer and Platform Tooling Image Separation

Implemented

Producer & Platform Tooling Image Separation

Context: Bundling heavy diagnostic packages (ClickHouse client, PySpark, PyIceberg) with the synthetic event producer created bloated images and slow rebuild times.

Decision: Separate into deliveryflow-producer (lightweight, minimal dependencies) and deliveryflow-tools (full diagnostic and one-shot runner toolkit).

Consequences: Producer image rebuilds in seconds; tooling updates do not trigger producer redeployments.

Context: Bloated container images containing both runtime services and management CLI utilities slow down builds and increase memory footprint.

Decision: Split into dedicated images: lightweight runtime producer image vs platform tooling image.

Consequences: Fast container boot, reduced disk overhead, and clean container lifecycle isolation.

ADR-012 Implemented

Modular Producer Architecture & Monotonic Rate Limiting

Implemented

Modular Producer Architecture & Monotonic Rate Limiting

Context: Monolithic generator script and naive time.sleep() loops caused cumulative timestamp drift during sustained streaming runs.

Decision: Refactor producer into clean submodules (config, events, source, streaming) and employ monotonic fixed deadline pacing.

Consequences: Zero clock drift during continuous simulation; highly modular code with dedicated unit tests.

Decision: Refactor producer into clean submodules (config, events, source, streaming) and employ monotonic fixed-deadline pacing.

Core Operational Principles

  • Config Validation: Run docker compose config --quiet whenever environment variables or service definitions are modified.
  • Config Validation: Run docker compose config --quiet or make config whenever environment variables or service definitions are modified.
  • Schema Drift Management: Run make purge whenever table definitions are restructured to avoid conflicting volume schemas.
  • Serving Layer Boundary: Superset dashboards must query prepared ClickHouse views, never raw Kafka topics or MinIO Parquet files directly.
  • Batch Readiness Check: The daily KPI Spark batch job requires at least one completed delivery streaming lifecycle before execution.
  • Job Submission Order: Submit the Flink streaming jobs (make flink-submit) prior to launching high-volume event producers.
  • Job Submission Order: Submit Flink streaming jobs (make submit-flink-job) prior to launching high-volume event producers.
