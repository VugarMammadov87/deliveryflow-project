DeliveryFlow Application Workflow

Multi-Application Workflow Update

DeliveryFlow now contains two stream applications. The original delivery application remains the default path, and the fleet vehicle telemetry application is selected explicitly with APP=fleet.

Delivery operations:


Synthetic producer -> Kafka delivery-events -> DeliveryStreamingJob -> ClickHouse delivery.* -> Superset

Fleet telemetry:


Synthetic producer APP=fleet -> Kafka vehicle-telemetry-events -> VehicleTelemetrySqlJob -> ClickHouse fleet.*

Fleet telemetry is implemented with Java + Flink SQL/Table API so the repository demonstrates a second streaming style without changing the existing Java DataStream delivery job. The job writes raw telemetry, current vehicle state, health alerts, and five-minute metrics into the fleet ClickHouse database.

Fleet commands:


make submit-flink-job APP=fleet
make produce APP=fleet
make test-e2e APP=fleet

Fleet ownership files:

  • configs/applications/fleet.yaml
  • configs/datasets/fleet/vehicle_telemetry.yaml
  • src/contracts/fleet/vehicle_telemetry_v1.schema.json
  • services/flink/src/main/java/local/deliveryflow/VehicleTelemetrySqlJob.java

This document explains step by step how applications, services, and batch and stream processes work in DeliveryFlow. It does more than list the services: it shows where data originates, which services process it, where it is stored, and how it appears as a report in Superset.

Overall Logic

DeliveryFlow is a logistics data platform built on local Docker Compose. It represents the same business domain through two data flows:

  • Stream processing: real-time delivery events move from Kafka to Flink and then to ClickHouse.
  • Batch processing: source and serving data are read by Spark, written to the Iceberg/Nessie/MinIO layer, and the KPI results are published back to ClickHouse.

One Generator Application

Generator file:


src/producers/synthetic_logistics_producer.py

The entrypoint contains only workflow orchestration and backward-compatible imports. The producer implementation is split into modules by responsibility:


src/producers/config.py       -> environment configuration and validation
src/producers/events.py       -> Delivery and Fleet event builders
src/producers/source.py       -> PostgreSQL batch/source seed
src/producers/streaming.py    -> Kafka transport and continuous pacing

This application produces two data types:

  • Batch/source data for PostgreSQL.
  • Stream delivery events for Kafka.

Select the mode with PRODUCER_MODE:

  • stream: publishes only Kafka events.
  • batch: seeds only the PostgreSQL source tables.
  • both: seeds PostgreSQL first, then publishes Kafka events.

Default local mode:


PRODUCER_MODE=both

Overall Platform Logic

        

          DeliveryFlow represents the same logistics business domain through two complementary data processing flows:
        

        
    
          
  • Real-Time Stream Processing: Asynchronous order events and IoT telemetry move from the synthetic producer to Kafka, are transformed with event-time semantics by Flink, and land in ClickHouse within milliseconds.
    • 
          
  • Analytical Batch Processing: On a scheduled cadence, Airflow verifies ClickHouse source readiness and triggers Spark batch jobs to join streaming events with dimensional PostgreSQL tables, committing ACID snapshots into Iceberg and publishing daily KPIs back to ClickHouse.
    • 
        


services/tooling/Dockerfile
    -> platform-tools and superset-importer
    -> health, E2E, and BI-as-Code import tooling

make produce and make produce APP=fleet use the minimal producer image. make health, make test-e2e, and make import-superset-assets run from the one-shot tooling image. Command names and generator behavior remain unchanged.

The events generated by the application simulate different stages of the logistics process:

  • ORDER_LOADED
  • VEHICLE_DEPARTED
  • IN_TRANSIT
  • DELIVERY_DELAYED
  • DELIVERED

The event payload now contains more than status and coordinates. It includes richer fields for reporting:

  • service_level
  • priority
  • customer_id
  • destination_city
  • package_count
  • order_value
  • payment_method
  • planned_distance_km
  • traffic_condition
  • weather_condition

Continuous Stream Mode

The stream generator can run as a continuous service instead of stopping after one run. The producer-continuous service starts with PRODUCER_MODE=stream and PRODUCER_CONTINUOUS=true.

Default rate:


PRODUCER_CONTINUOUS_INTERVAL_SECONDS=60
PRODUCER_EVENTS_PER_INTERVAL=10

This publishes a batch of 10 events to the Kafka delivery-events topic every 60 seconds. The batch-of-10 approach keeps rate tests simple, while monotonic-deadline pacing prevents event serialization and Kafka flush time from accumulating into the next interval. This mode is useful for verifying that event volume, latest delivery state, and vehicle utilization charts update over time in Superset.

Start the continuous producer manually:


make produce-continuous

View the logs:


make logs-producer-continuous

Stop the continuous producer:


make stop-continuous-producer

Kafka Role

Purpose: Kafka is the distributed event transport layer for all asynchronous domain messages.

Why it exists: It decouples event generators from stream processing consumers and buffers incoming real-time traffic reliably.

Input: Raw JSON event payloads published by the synthetic producer.

Output: Partitioned, ordered event streams consumed by downstream Flink jobs.

Consumer: Flink streaming applications (DeliveryStreamingJob and VehicleTelemetrySqlJob).

Example: The delivery-events topic carries delivery lifecycle events keyed by delivery_id. The vehicle-telemetry-events topic carries telemetry metrics keyed by vehicle_id.

Flink Role

Purpose: Flink performs stateful, low-latency stream processing and operational projections.

Why it exists: It provides sub-second transformations, event-time windowing, schema validation, and writes current-state snapshots directly into the serving layer.

Input: Versioned JSON events from Kafka topics (delivery-events and vehicle-telemetry-events).

Output: Validated operational state records and immutable event records written via HTTP JSONEachRow into ClickHouse.

Consumer: ClickHouse operational serving tables (delivery.* and fleet.*), which are subsequently read by Apache Superset dashboards.

Primary Jobs:

  • DeliveryStreamingJob.java: Java DataStream API pipeline for the Delivery application.
  • VehicleTelemetrySqlJob.java: Java Flink SQL/Table API pipeline for the Fleet application.

Sink: ClickHouseDeliverySink.java writes to three delivery serving tables:

  • delivery.delivery_events (immutable audit history)
  • delivery.delivery_current_state (latest state per delivery)
  • delivery.vehicle_current_state (latest state per vehicle)

Synthetic Domain Generator

        

          The generator application (src/producers/synthetic_logistics_producer.py) drives all test and demonstration data across the platform. In accordance with ADR-009 and ADR-012, it is architected with modular responsibilities:
        


    A->>CH: Check that delivery_events is not empty
    A->>SP: Submit daily_kpi_job.py with spark-submit
    SP->>CH: Read delivery.delivery_events
    SP->>SP: Calculate enrichment and KPIs
    SP->>I: Write bronze.raw_delivery_events
    SP->>I: Write gold.daily_delivery_kpi
    I->>N: Commit metadata
    I->>M: Store data and metadata files
    SP->>CH: Publish daily_delivery_kpi
    S->>CH: Read KPIs for the dashboard

Spark Role

Purpose: Spark is the distributed batch computation engine for heavy historical aggregations and Lakehouse management.

Why it exists: It handles large-scale data transformation, analytical KPI computation, and Iceberg bronze/gold table management with ACID guarantees.

Input: Event history from ClickHouse delivery.delivery_events and relational source data from PostgreSQL logistics_source.

Output:

  • Analytical Parquet files committed to Iceberg tables via Nessie catalog.
  • Aggregated daily KPI rows published to ClickHouse delivery.daily_delivery_kpi.

Consumer:

  • Long-term analytics queries running against Iceberg.
  • Superset daily KPI charts querying ClickHouse.

Primary Job: src/etl/apps/daily_kpi_job.py calculates key operational metrics:

  • completed deliveries
  • delayed deliveries
  • on-time deliveries
  • delay rate and on-time rate
  • average delay minutes
  • average vehicle utilization
  • total order value and package count
  • average distance km

Airflow Role

Purpose: Airflow acts as the batch orchestration control plane and workflow scheduler.

Why it exists: It provides dependable task scheduling, SLA tracking, readiness verification, and dependency management for batch pipelines.

Input: Scheduled triggers (daily cron intervals or manual operator runs).

Output: Triggered container commands (spark-submit execution) and execution status logs.

Consumer: Platform operators and monitoring systems.

Primary DAG: dags/delivery_daily_kpi.py defines two sequenced tasks:

  • check_source_readiness: verifies that ClickHouse contains delivery_events data before triggering Spark.
  • run_spark_daily_batch: triggers the Spark daily KPI job inside the Spark master container.

Main Workflows

Start the Platform


          

            
Stream Engine

            
Apache Flink

            
Purpose: Stateful event-time streaming compute and real-time state projection.

            
Why it exists: Handles out-of-order events via watermarks, maintains delivery state, and computes tumbling window aggregations.

            
Input: Versioned JSON messages from Kafka topics.

            
Output: Validated operational records written via HTTP JSONEachRow into ClickHouse tables.

            
Primary Jobs: DeliveryStreamingJob.java (DataStream API) and VehicleTelemetrySqlJob.java (Table API/SQL).

          


          

            
Serving Layer

            
ClickHouse Analytics

            
Purpose: Low-latency columnar database for real-time serving and BI analytics.

            
Why it exists: Delivers sub-second queries across millions of rows without loading transactional databases or lakehouse files.

            
Input: Micro-batched JSON rows from Flink sinks and daily KPI summaries from Spark batch jobs.

            
Output: High-performance SQL query results and pre-aggregated analytical views.

            
Serving Engines: MergeTree for event logs; ReplacingMergeTree for current state.

          

        

        
Batch & Lakehouse Component Roles


        

          

            
Batch Orchestrator

            
Apache Airflow

            
Purpose: Workflow scheduler and batch control plane.

            
Why it exists: Provides deterministic scheduling, dependency management, SLA alerting, and source readiness sensors.

            
Input: Scheduled cron intervals or operator CLI triggers.

            
Output: Orchestrated task status and Spark job submission commands.

            
Primary DAG: dags/delivery_daily_kpi.py (verifies ClickHouse readiness, then submits Spark KPI job).

          


          

            
Batch Compute

            
Apache Spark (PySpark)

            
Purpose: Distributed batch engine for heavy joins and Lakehouse commits.

            
Why it exists: Computes historical delivery KPIs across ClickHouse events and PostgreSQL dimensions with ACID safety.

            
Input: ClickHouse event tables and PostgreSQL source tables over JDBC.

            
Output: Partitioned Iceberg tables in MinIO and aggregated KPI records in ClickHouse.

            
Primary Job: src/etl/apps/daily_kpi_job.py.

          


          

            
Lakehouse Core

            
Iceberg + Nessie + MinIO

            
Purpose: Modern Open Table Format Lakehouse storage.

            
Why it exists: Provides ACID transactions, time travel, schema evolution, and Git-like catalog branching on top of object storage.

            
Storage: MinIO S3 bucket s3://lakehouse/warehouse/.

            
Catalog: Project Nessie REST catalog tracking Bronze and Gold table snapshots.

Key Principles


    

  • Kafka provides event transport, not the analytical source of truth.
    • 

  • Flink writes real-time state and operational history.
    • 

  • Spark performs batch aggregation and lakehouse writes.
    • 

  • Iceberg/Nessie/MinIO provide long-term analytical storage.
    • 

  • ClickHouse is the serving layer.
    • 

  • Superset is the dashboard layer.
    • 

  • Airflow is the batch orchestration layer.
