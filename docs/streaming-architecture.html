Kafka Message Partitioning & Key Design

In distributed event streaming, preserving message ordering is paramount. When multiple events for the same delivery arrive (e.g. ORDER_LOADED → IN_TRANSIT → DELIVERED), out-of-order processing will cause state corruption in downstream tables.

🔑
Delivery Partition Key: delivery_id
By publishing to Kafka with delivery_id as the record key, Kafka's Murmur2 hash partitioner guarantees that every lifecycle event for a specific transit always lands on the exact same topic partition. Consumers process each delivery strictly in chronological order.
Topic: delivery-events Partition Consistency
🔑
Fleet Partition Key: vehicle_id
Vehicle telemetry publishes hundreds of GPS and sensor pings per minute. By keying on vehicle_id, stateful stream computations (such as odometer distance integration and speed acceleration) run deterministically on a single consumer thread without cross-partition locking.
Topic: vehicle-telemetry-events Telemetry Affinity

Application 1: Delivery Operations (Java DataStream API)

Source Code: services/flink/src/main/java/local/deliveryflow/DeliveryStreamingJob.java
ClickHouse Sink: services/flink/src/main/java/local/deliveryflow/ClickHouseDeliverySink.java

The delivery streaming application is written using Flink's low-level DataStream API in Java. It consumes raw JSON messages from Kafka, validates schema versioning, manages event-time watermarks, and writes multi-projection records into ClickHouse.

Technical Implementation Details

  • Checkpointing Strategy: Checkpointing is configured at 10,000ms (10 seconds) intervals with CheckpointingMode.AT_LEAST_ONCE and a 60-second timeout. This provides low latency state commits while allowing ClickHouse's ReplacingMergeTree to deduplicate replayed records during recovery.
  • Watermarking: Uses WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(30)).withIdleness(Duration.ofMinutes(1)). This accommodates up to 30 seconds of network transmission jitter without dropping late events.
  • Contract Filtering: Events pass through a custom filter verifying schemaVersion == 1 and a non-blank eventId. Malformed payloads are discarded before reaching the sink.
  • State Partitioning: Events are keyed by event.deliveryId using Flink's keyBy() operator.

ClickHouse Multi-Projection HTTP Sink

Rather than requiring a heavy native JDBC driver, ClickHouseDeliverySink writes directly to ClickHouse using HTTP POST with FORMAT JSONEachRow. For every event received, Flink materializes three distinct projections:

ClickHouse Target Table Engine Deduplication / Key Logic Purpose
delivery.delivery_events MergeTree ORDER BY (delivery_id, event_timestamp, event_id) Complete immutable historical ledger; partitioned monthly with a 30-day automatic TTL drop.
delivery.delivery_current_state ReplacingMergeTree(version) ORDER BY delivery_id; version is eventTimestamp in epoch milliseconds. Instant state lookup for dispatchers. Contains calculated flags: is_delayed = delay_minutes > 0 and utilization = used / total.
delivery.vehicle_current_state ReplacingMergeTree(version) ORDER BY vehicle_id; version is eventTimestamp in epoch milliseconds. Real-time vehicle GPS position, active transit route ID, and load capacity.

Application 2: Vehicle Fleet Telemetry (Flink SQL)

Java Orchestrator: services/flink/src/main/java/local/deliveryflow/VehicleTelemetrySqlJob.java
SQL Definition: services/flink/src/main/resources/sql/fleet/vehicle_telemetry.sql

The fleet telemetry application demonstrates modern declarative stream processing with Flink SQL. It registers Kafka as an external streaming table and executes continuous streaming transformations in real time.

1. Kafka Streaming Source DDL

Flink SQL registers the Kafka topic with native ISO-8601 JSON decoding and a 10-second bounded watermark:

Flink SQL — Kafka Source DDL 
CREATE TABLE vehicle_telemetry_source (
    schema_version INT,
    event_id STRING,
    event_type STRING,
    event_timestamp TIMESTAMP_LTZ(3),
    ingestion_timestamp TIMESTAMP_LTZ(3),
    vehicle_id STRING,
    driver_id STRING,
    latitude DOUBLE,
    longitude DOUBLE,
    speed_kmh DOUBLE,
    fuel_level_pct DOUBLE,
    engine_temperature_c DOUBLE,
    odometer_km DOUBLE,
    engine_status STRING,
    vehicle_status STRING,
    WATERMARK FOR event_timestamp AS event_timestamp - INTERVAL '10' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'vehicle-telemetry-events',
    'properties.bootstrap.servers' = 'kafka:9092',
    'properties.group.id' = 'fleet-vehicle-telemetry-sql',
    'scan.startup.mode' = 'earliest-offset',
    'format' = 'json'
);

2. Real-Time Anomaly Detection & Safety Alerts

Continuous queries evaluate diagnostic metrics against operating safety limits and route violations directly to fleet.vehicle_health_alerts:

Alert Type Threshold Condition Severity Level Operational Consequence
OVERSPEED speed_kmh >= 100.0 km/h Warning Driver safety warning, speed governor audit log.
LOW_FUEL fuel_level_pct <= 15.0% Warning Refueling prompt dispatched to nearest warehouse route stop.
ENGINE_TEMPERATURE_HIGH engine_temperature_c >= 105.0 °C Critical Immediate pull-over instruction to prevent engine block failure.

3. 5-Minute Tumbling Window Metric Computation

Flink SQL aggregates rolling 5-minute diagnostic summaries across the entire active fleet using Window Table-Valued Functions (TVF):

Flink SQL — 5-Minute Tumbling Window 
SELECT
    window_start,
    window_end,
    COUNT(DISTINCT vehicle_id) AS active_vehicle_count,
    AVG(speed_kmh) AS avg_speed_kmh,
    AVG(fuel_level_pct) AS avg_fuel_level_pct,
    MAX(engine_temperature_c) AS max_engine_temperature_c,
    SUM(CASE WHEN speed_kmh >= 100.0 THEN 1 ELSE 0 END) AS overspeed_vehicle_count,
    SUM(CASE WHEN fuel_level_pct <= 15.0 THEN 1 ELSE 0 END) AS low_fuel_vehicle_count
FROM TABLE(TUMBLE(TABLE vehicle_telemetry_source, DESCRIPTOR(event_timestamp), INTERVAL '5' MINUTES))
WHERE schema_version = 1 AND event_type = 'VEHICLE_TELEMETRY'
GROUP BY window_start, window_end;

ClickHouse Real-Time Serving Mechanics

ClickHouse is configured to handle high-frequency streaming writes without lock contention or excessive partition fragmenting:

&zap;
ReplacingMergeTree Deduplication
Tables like delivery_current_state use ENGINE = ReplacingMergeTree(version). When events for the same delivery_id are written repeatedly, ClickHouse retains the row with the highest version (epoch milliseconds of event_timestamp) during background merges or on queries with FINAL.
Idempotent Ingestion State Deduplication
⏳
30-Day TTL Partition Retention
The immutable history table delivery_events defines TTL toDateTime(event_timestamp) + INTERVAL 30 DAY. ClickHouse automatically purges expired event partitions in the background, keeping local storage footprint small while preserving full historical depth in the Lakehouse.
Monthly Partitions Automated Pruning

Streaming Lifecycle & Runbook Commands

Manage and inspect streaming pipelines using bundled Makefile targets:

bash — Streaming Execution Runbook
# 1. Submit the default Java DataStream delivery job to Flink
make submit-flink-job
# 2. Produce synthetic delivery lifecycle events to Kafka
make produce-stream
# 3. Submit the Flink SQL vehicle fleet telemetry application
make submit-flink-job APP=fleet
# 4. Stream vehicle IoT diagnostic telemetry
make produce APP=fleet
# 5. Run automated end-to-end assertions against ClickHouse
make test-e2e
make test-e2e APP=fleet
