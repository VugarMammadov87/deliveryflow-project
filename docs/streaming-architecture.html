Streaming Architecture

DeliveryFlow implements two independent production-grade stream processing applications with Apache Kafka, Apache Flink, and ClickHouse: a DataStream API application for delivery operations and a Table API/SQL application for fleet vehicle telemetry.

Streaming Architecture Overview

The streaming layer ingests asynchronous domain events, validates them against strict schema contracts, tracks entity state, and publishes operational rows into ClickHouse serving tables in real time.

Event Contracts & Topics

Each application has an isolated Kafka topic and a versioned JSON schema contract located in src/contracts/<domain>/:

Application Kafka Topic Message Key Contract Schema Key Attributes
Delivery (Default) delivery-events delivery_id src/contracts/delivery/delivery_event_v1.schema.json schema_version, event_type, delivery_id, status, delay_minutes, capacity_used
Fleet (APP=fleet) vehicle-telemetry-events vehicle_id src/contracts/fleet/vehicle_telemetry_v1.schema.json vehicle_id, speed_kmh, fuel_level_pct, engine_temperature_c, engine_status
Why Key Messages?

Publishing messages with a business key (e.g. delivery_id or vehicle_id) guarantees that all sequential events for that specific entity are assigned to the same Kafka partition, preserving chronological ordering without requiring a single global partition.

Application 1: Delivery Operations (DataStream API)

Implementation: services/flink/src/main/java/local/deliveryflow/DeliveryStreamingJob.java

The delivery streaming job handles parcel order progression through various milestone events (ORDER_LOADED, VEHICLE_DEPARTED, IN_TRANSIT, DELIVERY_DELAYED, DELIVERED).

Key Technical Decisions

  • Checkpointing: Enabled at 10-second intervals with CheckpointingMode.AT_LEAST_ONCE and a 60-second timeout.
  • Watermarking: Uses WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(30)) with 1-minute idleness detection to handle network jitter.
  • Validation: Enforces schema_version == 1, rejects malformed payloads, and keys by delivery_id.
  • HTTP Sink: ClickHouseDeliverySink.java writes to ClickHouse using HTTP JSONEachRow format. This keeps the local deployment free from heavy binary driver overhead.

Target Serving Tables in ClickHouse delivery.*

  • delivery.delivery_events: Complete immutable event ledger (Engine: MergeTree, 30-day TTL).
  • delivery.delivery_current_state: Latest state per delivery, deduplicated by timestamp version (Engine: ReplacingMergeTree(version)).
  • delivery.vehicle_current_state: Latest location and utilization per vehicle (Engine: ReplacingMergeTree(version)).

Application 2: Fleet Telemetry (Flink SQL)

Implementation: services/flink/src/main/java/local/deliveryflow/VehicleTelemetrySqlJob.java
SQL Queries: services/flink/src/main/resources/sql/fleet/vehicle_telemetry.sql

The fleet telemetry application runs alongside the delivery pipeline as an independent streaming application. It processes continuous GPS and diagnostic streams using Flink SQL and the Table API.

Core SQL Pipeline Queries

The Flink SQL pipeline executes four parallel continuous queries from a single Kafka source table:

  1. Raw Telemetry Sink: Streams clean, validated telemetry records directly into fleet.vehicle_telemetry_events.
  2. Current State Tracking: Emits point-in-time vehicle status to fleet.vehicle_current_state.
  3. Health Alerting Filter: Evaluates threshold breaches in real time and routes alerts to fleet.vehicle_health_alerts:
    • Overspeed Alert: speed_kmh >= 100.0 (Severity: warning)
    • Low Fuel Alert: fuel_level_pct <= 15.0% (Severity: warning)
    • High Engine Temp: engine_temperature_c >= 105.0 °C (Severity: critical)
  4. 5-Minute Tumbling Window Aggregation: Computes rolling metrics using Flink's window table-valued functions:
SQL — Fleet 5-Minute Tumbling Window (vehicle_telemetry.sql) 
SELECT
    window_start,
    window_end,
    COUNT(DISTINCT vehicle_id) AS active_vehicle_count,
    AVG(speed_kmh) AS avg_speed_kmh,
    AVG(fuel_level_pct) AS avg_fuel_level_pct,
    MAX(engine_temperature_c) AS max_engine_temperature_c,
    SUM(CASE WHEN speed_kmh >= 100.0 THEN 1 ELSE 0 END) AS overspeed_vehicle_count,
    SUM(CASE WHEN fuel_level_pct <= 15.0 THEN 1 ELSE 0 END) AS low_fuel_vehicle_count
FROM TABLE(TUMBLE(TABLE vehicle_telemetry_source, DESCRIPTOR(event_timestamp), INTERVAL '5' MINUTES))
WHERE schema_version = 1 AND event_type = 'VEHICLE_TELEMETRY'
GROUP BY window_start, window_end;

Operational Streaming Commands

Manage and verify the streaming pipelines using standard Makefile targets:

PowerShell — Streaming Lifecycle Commands 
# Submit default delivery streaming job
make submit-flink-job

# Produce delivery stream events
make produce-stream

# Submit fleet Flink SQL streaming job
make submit-flink-job APP=fleet

# Produce fleet telemetry events
make produce APP=fleet

# Run automated end-to-end assertions against ClickHouse
make test-e2e
make test-e2e APP=fleet
Verify in UIs

Monitor streaming jobs in the Flink Web UI at http://localhost:8081 and inspect Kafka topics in the Kafka UI at http://localhost:8083.
