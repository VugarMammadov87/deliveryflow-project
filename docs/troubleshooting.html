Platform Troubleshooting Guide

Structured operational diagnosis workflows for common failure modes across ingestion, stream processing, analytical serving, lakehouse batch jobs, and BI dashboards.

Universal Diagnostic Command

Whenever you encounter anomalous behavior, run the automated multi-service health checker first. It probes all 8 platform endpoints and prints an immediate status summary:

Health Check 
make health

Diagnostic Triage Workflow

When triaging pipeline issues, isolate failures along the data path from ingestion to visualization:

1. Ingestion
Kafka Topics
Verify topic existence and event arrival
→
2. Processing
Flink Jobs
Check JobManager UI for checkpoints & exceptions
→
3. Serving
ClickHouse Rows
Query row counts and table engine states
→
4. BI & Batch
Superset / Spark
Verify catalog metadata and query views

1. Kafka Receives No Events / Producer Fails

Ingestion Issue

Producer completes but Kafka topic remains empty

Problem: Events are not appearing in the target Kafka topic (delivery-events or vehicle-telemetry-events).

Symptoms:

  • Kafka consumer offsets remain at 0.
  • ClickHouse tables receive zero new rows after running demo commands.
  • Flink stream processing metrics show 0 records read.

Possible Causes:

  1. The synthetic producer container exited prematurely due to missing environment variables or DNS resolution failure for kafka:9092.
  2. Kafka KRaft controller is still initializing cluster metadata and not accepting client connections.
  3. Topic auto-creation is disabled and the topic was not created prior to publishing.

How to Check:

Check Producer Logs & Topics 
# Check producer container logs
docker compose logs producer

# Inspect Kafka topic list directly inside the broker
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --list

# Check message counts inside delivery-events
docker compose exec kafka /opt/kafka/bin/kafka-run-class.sh \
  kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:9092 \
  --topic delivery-events

How to Fix:

  1. Ensure Kafka broker is healthy: docker compose ps kafka.
  2. If Kafka is healthy, trigger a manual producer run: make stream-demo.
  3. Verify that .env defines KAFKA_BOOTSTRAP_SERVERS=kafka:9092 for in-Docker networking.

Expected Result: Producer prints [INFO] Published 30 delivery events successfully and Kafka offset count increments.

2. Flink Streaming Job Fails or Stalls

Stream Processing

Flink DataStream or SQL Job in FAILED or RESTARTING State

Problem: Flink streaming jobs fail to deploy, terminate immediately, or repeatedly fail checkpoints.

Symptoms:

  • Flink Web UI at http://localhost:8081 displays job status as FAILED or RESTARTING.
  • ClickHouse tables are not updated despite messages existing in Kafka.
  • TaskManager log contains ConnectException: Connection refused to clickhouse:8123 or KafkaException.

Possible Causes:

  1. Flink job started before ClickHouse completed schema initialization.
  2. Event schema mismatch: JSON payload in Kafka does not match contract parsed by DeliveryEventParser.java.
  3. Flink TaskManager ran out of memory under heavy load or large tumbling window state.

How to Check:

Check Flink Logs 
# Check JobManager container logs
docker compose logs flink-jobmanager --tail=100

# Check TaskManager container logs
docker compose logs flink-taskmanager --tail=100

How to Fix:

  1. Verify ClickHouse is ready by running curl http://localhost:8123.
  2. Re-submit the Flink jobs to the cluster: make flink-submit.
  3. If schema validation failed, verify event structure with $env:PYTHONPATH="src"; pytest tests/test_event_contract.py.

Expected Result: Flink Web UI displays DeliveryStreamingJob and VehicleTelemetrySqlJob with green RUNNING status.

3. ClickHouse Serving Tables Stay Empty

Serving Layer

Queries return 0 rows despite active event generation

Problem: ClickHouse analytical queries return 0 rows in set.

Symptoms:

  • SELECT count() FROM delivery.delivery_events returns 0.
  • Superset charts show empty graphs with "No data returned".

Possible Causes:

  1. ClickHouse HTTP sink in Flink has not flushed the current batch buffer.
  2. Tables were created in the wrong database schema (e.g. default instead of delivery).
  3. Stale volume holds older schema lacking required tables.

How to Check:

Inspect ClickHouse Tables 
# Query ClickHouse directly via HTTP API
curl -s "http://localhost:8123/?query=SELECT%20database,%20name,%20total_rows%20FROM%20system.tables%20WHERE%20database%20IN%20('delivery','fleet')"

# Check ClickHouse server error log
docker compose logs clickhouse --tail=50

How to Fix:

  1. Wait 3-5 seconds for Flink HTTP sink batch timeout to flush pending events.
  2. Verify database schemas exist: docker compose exec clickhouse clickhouse-client --query "SHOW DATABASES".
  3. If tables are missing, re-run schema init: docker compose exec clickhouse clickhouse-client --multiquery < services/clickhouse/init/001_delivery_schema.sql.

Expected Result: ClickHouse returns row count matching produced event quantity.

4. Spark Batch Daily KPI Job Fails

Batch & Lakehouse

Spark Job Fails with Readiness Check or Catalog Error

Problem: make run-batch-kpi or Airflow task run_spark_daily_kpi fails with an exception.

Symptoms:

  • Airflow DAG execution status turns red (FAILED).
  • PySpark output displays RuntimeError: Source ClickHouse table has 0 records. Readiness check failed.
  • Iceberg commit fails with NessieNotFoundException: Branch main not found.

Possible Causes:

  1. The batch job was executed against a fresh platform where no streaming events have been produced yet.
  2. MinIO S3 storage bucket lakehouse was not created or credentials do not match spark-defaults.conf.
  3. Project Nessie REST catalog was not accessible at http://nessie:19120/api/v1.

How to Check:

Validate Batch Prerequisites 
# Verify ClickHouse source has events
curl -s "http://localhost:8123/?query=SELECT%20count()%20FROM%20delivery.delivery_events"

# Verify MinIO bucket existence
curl -s http://localhost:9001/minio/health/live

# Verify Nessie catalog status
curl -s http://localhost:19120/api/v1/config

How to Fix:

  1. Generate source streaming events first: make stream-demo.
  2. Wait 5 seconds for events to land in ClickHouse.
  3. Re-run the Spark batch job: make run-batch-kpi.

Expected Result: Spark computes dimensional joins and writes committed Iceberg snapshot to nessie.delivery.delivery_daily_kpi.

5. Superset Charts Display Errors

BI & Visualization

Chart shows "Error loading data" or Schema Mismatch

Problem: Superset dashboard charts display red error banners or fail to load query results.

Symptoms:

  • Dashboard cards show Table 'delivery.v_delivery_realtime_overview' does not exist.
  • ClickHouse database connection test in Superset fails.
  • Cached chart errors persist after data is populated.

Possible Causes:

  1. Superset database connection was not imported or points to incorrect credentials.
  2. Browser cache is serving stale metadata from a prior session.
  3. ClickHouse analytical views were not created in the database.

How to Check:

Check BI Assets 
# Re-run automated asset importer
make superset-import

# Verify views in ClickHouse
curl -s "http://localhost:8123/?query=SHOW%20TABLES%20FROM%20delivery%20LIKE%20'v_%25'"

How to Fix:

  1. Run make superset-import to ensure database connection and 5 chart assets are synchronized.
  2. Perform a hard refresh in your web browser: Ctrl + F5 (Windows) or Cmd + Shift + R (macOS).
  3. In Superset, click Settings → Clear Cache.

Expected Result: All 5 charts render operational KPIs, time-series lines, and donut distributions cleanly.

6. Port Conflict on Host Machine

Host Environment

Docker fails to bind local port (Port Already Allocated)

Problem: make up fails with error: Bind for 0.0.0.0:5433 failed: port is already allocated.

Symptoms: Docker Compose exits with code 1 during container startup.

Possible Causes: A native service running on the host machine (e.g., local PostgreSQL on 5432/5433, local Kafka on 9092, or local web server on 8080) is occupying the port.

How to Check:

Find Conflicting Port 
# On Windows PowerShell (e.g. check port 5433)
Get-NetTCPConnection -LocalPort 5433 | Format-Table -Property LocalAddress, LocalPort, OwningProcess

# On Linux / macOS
lsof -i :5433

How to Fix:

  1. Stop the conflicting host service via Services control panel or process manager.
  2. Alternatively, change the exposed host port in your .env file (e.g. set POSTGRES_SOURCE_PORT=5435).

Expected Result: Docker Compose successfully binds all host ports during make up.

7. Corrupted State or Schema Drift

State Reset

Resetting Stale Named Volumes (make purge)

Problem: Underlying database schemas or catalog metadata have drifted after updating repository files, and new migrations conflict with old volume data.

How to Fix (Factory Reset):

Destructive Action Warning

This command deletes all persistent Docker volumes, wiping all data in PostgreSQL, ClickHouse, MinIO, and Nessie.

Factory Reset 
# 1. Stop containers and destroy named volumes
make purge

# 2. Re-launch platform with fresh initialization schemas
make up

# 3. Verify health
make health

# 4. Re-seed dimensional data and run stream demo
make seed-postgres
make stream-demo

Expected Result: All 12 services restart with pristine schemas matching repository source files.
