Batch & Lakehouse Architecture

DeliveryFlow implements an open-table Lakehouse architecture using Apache Iceberg, Project Nessie, MinIO, Apache Spark, and Apache Airflow to compute, store, and publish daily logistics key performance indicators (KPIs).

Lakehouse Architecture Overview

While the streaming pipeline serves immediate operational status, the Lakehouse path guarantees long-term analytical persistence, reproducible historical snapshots, and aggregated KPI reporting.

Distinction of Lakehouse Roles

In a modern Lakehouse, storage, table format, catalog, and compute are independent modular layers. DeliveryFlow keeps these responsibilities strictly separated:

MinIO

Object Storage
Physical Storage Layer

Provides local S3-compatible object storage. Holds the actual physical Parquet data files, Iceberg metadata JSON files, and manifest lists in bucket delivery-lakehouse.

Apache Iceberg

Table Format
Open Table Format

Organizes physical Parquet files into ACID tables. Provides atomic snapshot isolation, schema evolution, and hidden partitioning without directory-structure coupling.

Project Nessie

Catalog
Transactional Table Catalog

Tracks which Iceberg metadata file corresponds to the current table state. Provides Git-like branch, tag, and commit semantics over tables (persisted in PostgreSQL).

Apache Spark

Compute Engine
Distributed Batch Engine

Executes large-scale transformations, reads source facts via JDBC, commits Iceberg tables using the Nessie catalog, and publishes results back to ClickHouse.

The Batch Execution Flow

1. Orchestration via Apache Airflow

DAG File: dags/delivery_daily_kpi.py

Airflow functions purely as a scheduler and control plane, not as an execution runtime. The DAG enforces a strict sequence:

  1. check_source_readiness: Executes a lightweight Python check against ClickHouse to verify that delivery.delivery_events contains rows. If the streaming path has not run yet, the DAG fails early to prevent publishing empty KPI metrics.
  2. run_spark_daily_batch: Executes spark-submit --master spark://spark-master:7077 /opt/deliveryflow/src/etl/apps/daily_kpi_job.py inside the Spark cluster.

2. Spark Batch Application Logic

Entrypoint: src/etl/apps/daily_kpi_job.py

When triggered, the Spark application performs the following steps:

  • Extract: Reads delivery event facts from ClickHouse delivery.delivery_events using partitioned JDBC queries.
  • Transform: Calculates daily operational aggregations:
    • Total deliveries, completed deliveries, delayed deliveries, and on-time deliveries
    • Delay rate (delayed_deliveries / completed_deliveries) and on-time rate
    • Average delay in minutes and average vehicle fleet utilization
    • Total parcel package count, total order value, and average distance in km
  • Lakehouse Commit (Bronze & Gold):
    • Writes raw event facts to nessie.bronze.raw_delivery_events
    • Writes curated daily KPI rows to nessie.gold.daily_delivery_kpi
  • Serving Layer Publication: Inserts the aggregated KPI rows into ClickHouse table delivery.daily_delivery_kpi using JDBC.

Iceberg Lakehouse Table Catalog

Namespace / Table Layer Partition Strategy Purpose
nessie.bronze.raw_delivery_events Bronze (Raw) Partitioned by event_date Immutable, queryable historical archive of all raw delivery stream events.
nessie.gold.daily_delivery_kpi Gold (Curated) Partitioned by business_date Enriched business metrics aggregated by date, region, and warehouse.
delivery.daily_delivery_kpi Serving (ClickHouse) Monthly (toYYYYMM) Columnar serving table queried by Apache Superset dashboard charts.
